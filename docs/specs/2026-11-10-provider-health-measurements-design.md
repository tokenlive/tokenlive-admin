# 供应商健康指标读取与有效性

状态：已实现并验证。

## 确认的规则

- 真实零值正常显示。没有样本、不支持、来源不可用或读取失败分别表达，页面显示“—”及原因；单项失败不丢弃其他可用项。
- 供应商调用数、成功／失败数、成功率来自上游尝试数据（Redis／内存）；不使用当前 Prometheus 最终 Request 计数替代。
- 保留现有性能卡片，标明请求级统计范围、数据来源与覆盖情况；不称为每次上游尝试自身的耗时。
- 继承第一部分的共同评估截点、显式时区、半开完整分钟窗口和部分覆盖策略。
- 保留整窗口 code 优先、名称兼容的规则；按存在性选择一次标识，不能按非零值或逐指标拼接 code/name。

## 已核实的源含义

Gateway `outbound/metrics.go` 每次最终 Request 记录一次 Prometheus 计数，provider label 当前为最终供应商名称；duration 和 TTFT 从请求起点计时，包含重试过程，性能样本并不限于成功请求。`status_collector.go` 则遍历 History，按每个 attempt 写 Redis provider 状态，优先 ProviderCode。

Admin MemoryStore 按 Attempts 记录调用结果，并将请求级性能归属到成功 attempt 的供应商。旧版无 Attempts 的归属请求性能继续保留，单独标记其范围，不当作上游尝试计数。因此性能必须区分“最终供应商归属的请求”与“成功调用供应商归属的请求”，不能声称两种性能样本完全等价。

## Interface 与范围

保留 `Reader.Read` seam 和 `Query.providers`。供应商行返回具名类型的 HealthMetric：值、状态、来源、统计范围、窗口、覆盖范围、稳定原因；成功／失败及总调用数原子返回并派生成功率。外层 Reading 汇总状态，但不会因一个指标失败而丢弃整行。

供应商计数只在 Redis 真实保留区间内读取，源失败或历史超出保留时回退本实例内存观测并明确来源；性能整组选用 Prometheus 或内存，各项错误独立。空值排序置后，不把未知供应商当作零调用静默过滤。

当前端点数和熔断数属于当前库存／运行时状态，独立于历史请求指标。供应商详情流量通过显式 `traffic.provider` 复用同一尝试观测；详情仍沿用现有查询编排；本轮不增加分位数、429/401 分类，不修改 Gateway 埋点。
