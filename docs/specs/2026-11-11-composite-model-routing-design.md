# 复合模型：业务入口与选模策略设计

状态：设计草案，尚未实现。日期：2026-11-11。

## 1. 目标与范围

复合模型提供一个稳定的业务模型编码，例如 `customer-service`。业务调用这个编码，平台在普通模型之间选模，并复用现有端点治理。模型替换不要求业务修改调用代码。

本次设计覆盖 Admin 与 Gateway。本文中的新字段、接口和行为均为拟议契约，不代表当前已经支持。先交付确定性的主备、规则模式与文本流式调用；原难度裁决作为兼容模式保留。智能分类、多模态、工具调用、动态成本/延迟优化留待后续，不同时引入工作流、多个模型投票或答案融合。

成功标准：管理员能解释一次请求为何选中某模型、失败后会调用谁，以及实际消耗和业务结算如何计算；业务能通过同一个模型编码使用非流式和流式文本 Chat Completions。

## 2. 代码核对与问题

| 当前事实 | 代码位置 | 设计影响 |
| --- | --- | --- |
| `smart` 强制裁决模型、连续覆盖 0–100、至少两个不同子模型 | `internal/mods/resource/schema/smart_routing.go` | 不能承载简单主备或先单模型接入的业务入口 |
| 配置以稳定模型 ID 保存，发布时解析为编码 | `internal/mods/resource/biz/smart_runtime.go` | 保留现有身份引用与发布边界 |
| 配置保存与启用分离，存在版本冲突检测、同步失败反馈 | `internal/mods/resource/biz/smart_routing_edit.go` | 延续这些行为，不把保存成功等同于生效成功 |
| 调用策略已有 `fallback_policy.targets` | `internal/mods/policy/schema/types.go` | 备用链只在调用策略中保存，选模 JSON 不再保存另一份 |
| 标签路由筛选端点，目的条件匹配端点 metadata | Gateway `pkg/routers/tag.go` | 复用条件匹配器，不能直接拿端点路由实现跨模型选模 |
| SmartRouter 自行裁决、向高档升级，子上下文主动清除 fallback | Gateway `pkg/invoker/smart.go` | 不能只扩展页面；需要统一新模式的跨模型执行机制 |
| 普通 FallbackInvoker 只对 `ErrNoAvailableEndpoint` 切换，并受首字节与亲和性保护 | Gateway `pkg/core/invoker.go` | 现有机制不能直接视作通用的 429/5xx/超时跨模型切换能力 |
| 当前 smart 请求解析主动拒绝 stream、tools、非文本输入 | Gateway `pkg/invoker/smart_request.go` | 新模式需要独立的请求能力解析，不能简单删除校验 |
| 运行记录已有配置版本、实际模型、裁决耗时与升级原因 | Gateway `pkg/core/smart_routing_runtime.go` | 扩展现有记录，不另起一套无关联日志 |

Gateway 路径均相对于同级 `tokenlive-gateway` 仓库。本次只读取该仓库，未修改运行逻辑。

## 3. 职责与配置归属

| 对象 | 唯一职责 | 配置位置 |
| --- | --- | --- |
| 模型别名 | 同一模型的另一调用名称 | 现有 ModelAlias |
| 普通模型 | 确定的模型能力及供应商端点集合 | 现有 Model / Endpoint |
| 复合模型 | 业务能力承诺、首次选模 | Model 的路由配置 |
| 复合模型调用策略 | 跨模型备用链、切换条件、请求预算 | 该复合模型所属的 Invocation 策略实例 |
| 子模型治理 | 目标授权、限额、端点路由、熔断和端点重试 | 普通模型的有效治理策略 |

同一请求只允许一个跨模型调度者。新模式通过一个请求级执行器组织首次选模和备用链；子模型执行禁用其跨模型 fallback，保留端点治理。不得在 SmartRouter 外再套一层独立 fallback 循环。

沿用模型策略实例的作用域与合并语义。不同租户/用户可具有不同有效备用链；页面必须区分“全局默认配置”和“指定身份生效配置”。不把全局默认链显示成所有用户的最终行为。

首次选模只由复合模型的选模配置负责；复合模型已有的端点标签路由不会自动变为选模规则。子模型的标签路由继续筛选其端点。

## 4. 选模方式

### 4.1 主备模式 `priority`

- 必填主模型；可以不配置备用模型，也不要求裁决模型。
- 首次选择主模型。备用模型来自复合模型的有效 Invocation 策略。
- 主模型不满足该请求能力或当前没有可用端点时，可按有效备用链选择；无合格目标则明确失败。
- 候选去重，禁止自身引用及嵌套复合模型。

### 4.2 规则模式 `rules`

- 必填默认模型；启用的规则按显式且唯一的 `order` 升序匹配，第一条命中即停止。
- 一期只允许结构化标签和经过白名单的业务 Header，复用已有条件与 AND/OR 匹配语义。
- 一条规则只指定一个普通目标模型，不引入加权目标组。
- 无规则命中时使用默认模型。
- 命中规则但目标不可用时进入有效备用链，不继续匹配下一条规则，也不自动回到默认模型。
- Header 和标签只能影响允许候选中的选模，不能作为授权、余额或配额依据。鉴权、供应商凭证等敏感 Header 禁止成为规则条件。
- 不通过正文关键词假装理解任务，也不在一期添加不可靠的跨模型统一 token 数阈值。

### 4.3 兼容难度模式 `difficulty`

现有无 `mode` 的配置按旧难度模式解释。保留原有分段、裁决异常处理和升级语义；不在后台静默改成新备用链。页面明确标记“难度裁决（兼容模式）”。

旧模式的执行循环暂时隔离，不能叠加新跨模型 fallback。以后转换成新模式须显式保存配置，展示转换前后的默认目标、备用链和裁决行为差异。

新智能模式后续再设计：任务类别、分类器版本、置信阈值和指定异常目标必须显式，不把任意 0–100 分当作通用质量指标。

## 5. 拟议数据契约

一期保留 `model_type=smart`、`smart_routing` 字段和当前 Redis key，避免把产品名称调整与存储改名绑在一起。增加 `schema_version` 表示格式；现有 `version` 继续表示配置修订号，两者不能混用。

主备模式的 Admin 持久化形态：

```json
{
  "schema_version": 2,
  "version": 1,
  "mode": "priority",
  "primary_model_id": "model-a-id"
}
```

规则模式的 Admin 持久化形态：

```json
{
  "schema_version": 2,
  "version": 1,
  "mode": "rules",
  "default_model_id": "model-a-id",
  "rules": [
    {
      "id": "rule-code",
      "name": "代码业务",
      "order": 10,
      "enabled": true,
      "relation_type": "AND",
      "conditions": [
        {"type": "TAG", "key": "task", "op_type": "EQUAL", "values": ["code"]}
      ],
      "target_model_id": "model-b-id"
    }
  ]
}
```

规则 ID 在修改和排序时保持不变。拒绝未知模式、未知条件类型、非法操作符、重复排序值、启用的空条件规则，以及不同模式字段混填；默认模型通过专用字段表达。

运行态契约将模型 ID 解析为模型编码，分别使用 `primary_model`、`default_model`、`target_model`。HTTP 拉取、Redis、嵌入式快照共用一个运行态类型。缺少 `schema_version` 的旧文档按格式 1 处理，未知格式必须拒绝，不能降格成普通模型。

备用链继续保存于 Invocation 的 `fallback_policy.targets`，不出现在上述 JSON。配置页面用模型选择器输入，聚合 API 可接收 `fallback_model_ids`，服务端事务内解析为现有策略中的模型编码。当前模型更新不修改 `model_code`；旧目标删除后编码被重新使用时，必须重新授权和验证，不能继承旧目标身份。依赖检查应以原模型 ID 建立关系或在事务内清除旧引用，不能仅按可复用编码认定身份。

删除保护和依赖展示须同时覆盖主模型、默认模型、规则目标、裁决模型、区间目标和所有绑定作用域中的备用目标。现有只扫描 `SmartRouting.ReferenceIDs()` 的实现不足以覆盖新设计。

## 6. 执行顺序与故障边界

1. 解析请求能力，固定复合模型配置与该调用身份的有效策略快照。
2. 执行入口鉴权、复合模型访问检查、业务余额和请求级限额预占。
3. 根据模式选出首次目标，生成去重后的“首次目标 + 有效备用链”。
4. 逐个检查目标权限、请求兼容性、可用端点；不合格目标记录原因，不向上游发送。
5. 为目标创建隔离子上下文，保留调用身份和业务标签，执行目标限额及端点调用链。
6. 按切换条件及统一预算决定继续或结束；每个子调用正确核销或释放自身预占。
7. 外层只执行一次业务结算和请求结束日志，保留复合入口及实际模型身份。

复合模型与每个目标均沿用当前调用身份授权。配置人的读取权限不等于调用人的使用权限；本期不引入“授权复合模型即隐式授权所有子模型”。页面提供按测试身份查看缺失目标权限的诊断。

| 事件 | 新模式行为 |
| --- | --- |
| 无端点、熔断或端点治理过滤后无可用候选 | 首字节前按备用链切换 |
| 目标不兼容或无使用权限 | 跳过该候选；无候选则返回相应分类错误；不公开无权查看的目标详情 |
| 上游 429、可重试 5xx、连接失败、目标调用超时 | 仅在显式允许、请求可重放、尚未提交响应且仍有预算时切换 |
| 本地硬配额、业务余额不足、客户端取消、总期限到达 | 终止，不能通过换模型绕过 |
| 入参错误、内容拒绝、凭证/配置错误 | 默认终止，不把一切非 2xx 都视为可切换 |
| 已提交响应头或任意响应体字节 | 终止透明切换；已开始流输出则按协议结束或报告中断 |
| 强制亲和性且不允许降级 | 保留现有约束，终止 |

复用现有错误解析和端点重试能力，但新跨模型切换需要结构化失败原因与策略开关；不能直接扩大普通 `CanFallbackModel` 的行为，使旧普通模型策略无意中改变。

请求预算由外层统一持有：`total_timeout_ms`、`max_model_attempts`、`max_upstream_attempts`。后两者均包含首次尝试；裁决调用如被启用也消耗总期限和上游尝试预算。具体默认值集中配置，不能散落于多个 Invoker。子模型端点重试消耗剩余预算，不能为每个新模型重新获得一份完整预算。

## 7. 能力承诺与流式行为

一期新模式支持文本 Chat Completions 的 `stream=false/true`。旧 difficulty 模式仍维持旧协议边界。tools、多模态、结构化输出等仅在后续能力链路验证完成后开放，不静默删除参数。

复合模型的上下文、最大输出和协议能力是业务承诺，而不是所有子模型能力的并集：保存和发布时必须证明至少有一条目标路径满足声明，运行时还需逐目标、逐端点检查完整请求。目标能力不明时不能当作支持。

上下文检查使用目标 tokenizer 或明确标记的保守估算，包含系统消息、历史、输出预算等；不能用裁决输入字节限制代替执行模型上下文校验。原始业务请求不截断。

新执行器不能继续把整段成功答案缓存在旧 `smartResponseBuffer` 中再返回。流式调用在提交响应前可检查/切换候选；一旦提交响应便直接透传该次输出，保持取消、背压、usage 和资源释放语义。提交响应的标记以真实 writer 状态为准，不以内部 TTFT 代替。

## 8. 页面与接口

模型详情中的“难度路由区间”调整为“选模配置”。新建复合模型默认主备模式，裁决器参数仅在旧难度模式内展示。

| 页面区域 | 内容 |
| --- | --- |
| 基本信息 | 业务用途、模型编码、声明能力、启用状态 |
| 选模配置 | 主备/规则/兼容难度；对应字段与默认目标 |
| 故障处理 | 同一模型 Invocation 策略的全局默认视图、作用域提示、备用顺序、切换条件和请求预算 |
| 路由预演 | 测试身份、请求与标签；展示规则命中、候选排除原因、计划目标、版本和预算 |
| 运行效果 | 实际模型占比、切换原因、延迟、成功率与成本 |

同一备用链在“故障处理”和“调用管理”中编辑的是同一策略实例。对于多个作用域策略，明确展示有效来源和优先级，不创建隐藏的第二份链。

拟议聚合接口（相对现有 resource v1 路由组）：

- `GET /models/:id/composite-config`：返回选模配置、可编辑调用策略及其版本、可见依赖与同步状态。
- `PUT /models/:id/composite-config`：事务内保存选模及显式提交的策略变更；校验双方版本，任一冲突整体失败；不自动启用。
- `POST /models/:id/route-preview`：以未发布草稿或指定已存版本进行确定性预演，不调用 LLM、不变更配额、不创建业务数据。

预演默认使用当前调用身份。模拟其他身份必须有单独权限；浏览器提交任意 tenant/user 字段不能赋予模拟权限。管理员拥有模型写权限也不能因此获得冒充调用身份的能力。

预演返回匹配规则 ID、计划首选模型、备用顺序、排除原因、配置/策略版本、能力检查结果和未知项。动态健康、负载、真实耗时及最终费用不可由纯预演保证；显示状态采集时间，不宣称一定会执行某个上游。

规则匹配与候选计划必须复用 Gateway 的纯计划函数，不能由前端或 Admin 再独立实现一套。实施时在两仓库确定可共享的纯 Go 契约/计划包；若以依赖形式引入，先验证不存在模块循环。无法共享时由 Gateway 提供同源预演端点，Admin 做鉴权代理，不能交付语义不同的“近似预演”。

已有 `PUT /models/:id/smart-routing` 兼容旧难度编辑，不承担新聚合保存语义。

## 9. 费用与观测

业务结算一期延续复合模型已有价格配置：一次成功请求按复合入口报价及最终答案 usage 结算；最终失败不收答案费用。上线前须用已有结算集成测试确认该规则与真实实现一致。裁决和失败调用的支出由平台承担，单独记录，不混入对外答案 usage；不同时上线另一种按子模型价格结算模式。

平台成本按每次上游实际用量及当时有效价格快照计算。失败尝试可能已经消耗 token，不能统一当作零成本；用量未知则标记未知，估算值与已知值分列。不能把退款式配额释放误认为供应商没有收费。

路由日志扩展现有记录：模式、格式/配置/策略版本、命中规则 ID、计划目标、实际目标、每次尝试及跳过原因、响应是否提交、预算终止原因。保留旧裁决字段，非裁决模式不伪造评分。

指标提供各目标请求占比、最终成功率、业务 TTFT/P95、跨模型切换率和耗时、平台成本与业务收入。request_id、用户 ID、规则 ID 等高基数字段放日志，不作为无界 Prometheus 标签。

“节省成本”使用固定基线、同一请求样本和同一价格口径比较；“质量可接受”使用离线任务样本评测，不能从成功率推断。未形成基线前不展示无依据的节省百分比。

## 10. 保存、发布与升级

- 延用草稿停用、手动启用、乐观版本冲突、同步失败可重试及请求内固定快照。
- 聚合保存返回路由与策略的新版本及发布状态。持久化成功、编译成功、发布成功分开表达。
- DB 事务不能保证多个 Redis key 同时可见。新增发布代次及 manifest，将选模定义、作用域策略版本、依赖身份关联为完整快照；Gateway 只切换到完整代次。不允许“新首选 + 旧备用链”拼装生效。HTTP/嵌入式导出遵循同样规则。
- 编译失败保留上一次完整配置并明确标记未生效。权限撤销、停用与删除仍须及时撤回相应访问，不能因保留旧快照继续使用已被撤销的目标。
- 发布前检查全作用域依赖。被引用的模型删除/转换应阻止并提示处理引用；停用允许但警告影响，运行时将其视为不可用。
- 发布版本标识不能在删除和编码复用后继承旧对象，补齐身份与代次校验。
- 新能力由服务端功能开关关闭起步，所有承载该空间流量的 Gateway 先升级到支持格式 2 与完整发布代次，再允许 Admin 发布新模式。开关只控制管理入口，不能代替 Gateway 的格式校验。
- 滚动升级时旧文档保持旧格式；旧 Gateway 不接收新模式。不能只依赖旧 Gateway 拒绝新文档，因为这会把兼容问题转化成业务 503。
- 回退旧 Gateway 前，须把新模式迁出流量或显式恢复可被旧 Gateway 执行的旧配置。新规则模式不能无损自动降成评分区间。

## 11. 分阶段交付

| 阶段 | 交付内容 | 验收门槛 |
| --- | --- | --- |
| A：契约与安全发布 | 新模式 DTO/校验、依赖身份、错误分类、统一预算、完整发布代次、旧模式兼容样例 | 两仓库契约样例一致；旧配置行为保持；部分发布不可生效 |
| B：主备可用 | 新执行器接入、复合调用策略复用、单候选、文本流式、聚合保存、主备页面、基础路由日志 | 无裁决调用；主备可控；提交响应后不切换；不越权或重复结算 |
| C：规则与预演 | 有序规则、默认模型、共享纯计划函数/同源预演、作用域诊断、效果页 | 预演和真实执行初始计划一致；动态差异有解释；无额外推理或数据副作用 |
| D：智能优化 | 任务分类器、离线回放、置信度/异常策略；再评估成本与延迟动态选择 | 在约定样本和质量门槛下证明收益，纳入裁决与失败调用成本 |

阶段 B 是第一个业务可使用版本；阶段 A 单独合入不宣称“新复合模型已可用”。阶段 C 复用 B 的执行和结算，不另建一条调用链。

## 12. 必要验收案例

1. 仅一个主模型，无裁决无备用，正常返回；后续增加备用不改变业务编码。
2. 主模型无端点，按有效备用链调用；同一模型不重复调用；作用域切换改变链而不绕过授权。
3. Header/标签首条命中、未命中默认、命中目标不可用、同优先级拒绝保存、敏感 Header 拒绝配置。
4. 目标上下文不足、目标停用、无权限和无兼容端点均可诊断；无合格目标无上游调用。
5. 允许的上游失败可切换；本地硬配额、余额、取消、总期限和强亲和约束终止。
6. 端点重试与模型切换共用预算，尝试数不按层相乘；所有预占正确释放/核销。
7. 流式响应提交前按允许条件切换；提交后断流不切换、不拼接第二个模型的输出；取消及时传播。
8. 一次成功业务结算、失败答案不计费；平台记录已知失败支出，未知 usage 不伪造成零。
9. 两人同时编辑路由或关联策略，聚合保存整体冲突；同步失败可重试且不会覆盖新版本。
10. Redis 部分写入、乱序事件、依赖停用、删除后编码复用、旧 Gateway 混部与回退均不产生错误路由。
11. 预演不调用供应商、不动配额、不写业务数据；越权身份模拟被拒绝；预演计划与执行共享逻辑。
12. 原 difficulty 配置、非流式约束及升级/裁决异常行为保持；普通模型原有 fallback 行为不变。

集成数据由 fixture 创建并在清理阶段删除；不以手工插入长期数据作为验收。实现阶段变更前端后执行 Prettier，并按改动运行相应 Go 与前端检查。
