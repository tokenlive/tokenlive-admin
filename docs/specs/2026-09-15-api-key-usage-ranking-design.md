# 首页 API Key 用量排行设计

日期：2026-09-15

状态：交互与范围已确认，书面设计待审核；尚未进入实施计划或业务代码开发。

## 1. 目标与范围

在首页总览回答：**哪些客户端 API Key 消耗最多，它们属于哪个应用或使用者？**

覆盖 Admin 用户 Key、租户 Key、Portal 工作空间 Key，不包含供应商上游密钥。保留现有首页模块，新增仅超级管理员可见的只读榜单。

首版不增加 Key 详情页、点击跳转、抽屉、逐条请求日志、密钥管理操作或告警功能，不新增计费、采集和数据回填系统。

## 3. 现有实现与约束

以下结论来自本地源码检查，不代表生产环境已部署或配置完成。

- 首页布局、时间筛选和模型榜单位于 `frontend/src/views/home/index.vue`。现有 WebSocket 每 5 秒推送一次，HTTP 降级轮询为 10 秒。
- Dashboard 当前使用 Prometheus、Redis 或内存指标；Admin 尚无 ClickHouse 客户端与配置。本功能需要新增可选的只读数据源接入，不能只增加前端组件。
- Gateway 的 `AccessLogItem` 包含 `workspace_id`、`api_key_id`、`api_key_hash`、脱敏 Key、模型、Token、费用及请求结果，并可写入 ClickHouse `access_logs`。
- Gateway 的 Redis 鉴权路径计算 Key Hash。Admin 用户 Key 的同步字段目前不包含 `key_id`，因此不能只按 `api_key_id` 分组。
- Admin 用户 Key 与租户保留逻辑删除记录；租户密钥可以被替换，当前租户记录不等于完整密钥历史。
- Portal 现有内部接口可以按工作空间读取 Key 的安全元数据，包括名称、脱敏片段和状态；该调用与 ClickHouse 用量查询是两个不同的数据源。
- Admin 与 Portal 用户体系不能混用，遵循 `CONTEXT.md` 与 ADR-0001。Portal 工作空间 Key 的归属不能仅凭一个同名用户或相同租户推断。
- Token 总量沿用 `docs/specs/2026-08-12-model-ranking-token-accuracy-design.md` 的输入＋输出口径。

## 4. 方案选择

采用 **Admin 只读查询 ClickHouse，再补充 Key 元数据**。

| 方案 | 取舍 |
| --- | --- |
| 直接查询现有 ClickHouse 日志（采用） | 利用已有 Key 标识与用量字段；需增加 Admin 只读接入及元数据解析 |
| 给现有 Prometheus 指标增加 Key 维度 | 需要修改网关指标，历史数据没有该维度，且与当前明细数据源形成另一条统计链路 |
| 新建独立用量采集与汇总系统 | 能单独规划长期报表，但超出本次首页榜单范围 |

首版不新建聚合表或物化视图。若部署环境的 7 天查询无法在约定时限内完成，应明确显示不可用，再以真实测量另行评估优化，不能静默缩短时间范围或采样冒充完整统计。

## 5. 组件与职责

1. **榜单 API**：认证及 Root 校验、参数白名单、统一响应和错误映射。
2. **榜单服务**：固定查询窗口，组合用量、全量分母与元数据，生成展示对象和警告。
3. **ClickHouse 只读查询层**：去重、Key 归并、汇总、排序、截取及全量统计，不读取或修改管理数据库。
4. **Key 元数据解析器**：从 Admin 数据库和已有 Portal 内部接口获取名称、归属及状态，查不到时保留用量。
5. **独立前端组件**：列表、筛选、悬停明细、30 秒刷新和异常状态，不加入现有 5 秒 WebSocket 载荷。

新增后端实现按 `internal/mods/dashboard` 下的 API、业务、查询与响应模型分离；不继续把独立功能全部堆进现有 `dashboard.api.go`。前端从首页提取独立 `APIKeyUsageRanking` 组件。具体文件划分在实施计划中落实。

主要修改范围为 Admin。首版复用 Gateway 和 Portal 已有能力，不默认修改它们的鉴权、计费或业务接口。

## 6. Key 身份与归属

### 6.1 聚合标识

- 优先以日志中的非空 `api_key_hash` 区分实际客户端凭证，不使用 Key 名称、脱敏字符串、用户 ID 或租户 ID 作为 Key 分组键。
- 缺少 Hash 时，只能使用经过对应来源元数据验证的稳定 Key ID；Portal ID 必须结合工作空间和来源，不能跨系统直接合并。
- 同一凭证的新旧记录分别带 Hash 和 ID 时，仅在有可靠一对一映射时归并。标识冲突或无法验证时，不进行猜测性合并。
- 两个不同 Hash 即使显示名称相同，也保持独立。租户替换密钥后，新旧凭证不能只因租户相同就合并。
- 没有可靠 Hash 或可验证 ID 的记录，归入“无法归属的历史用量”。

元数据补充失败不影响已具备可靠 Hash 的日志单独成行；它们不是“无法归属的历史用量”，而是“Key 已区分、信息暂不可用”。

### 6.2 展示元数据

| 来源 | 查找方式 | 名称与归属 |
| --- | --- | --- |
| Admin 用户 Key | 用现有 Hash 算法匹配用户 Key，读取包含逻辑删除项的记录 | Key 名称、Admin 用户；关联用户消失时保留其标识 |
| 租户 Key | 匹配租户当前或保留的 Key 记录，结合日志租户标识 | 无独立 Key 名称时显示“租户名称 · API Key”；旧密钥无法匹配时保留日志归属并标记信息不完整 |
| Portal 工作空间 Key | 按日志工作空间和 Key ID，调用已有 Portal 内部接口 | Key 名称、工作空间标识；名称可获得时补充工作空间名称 |
| 来源暂不可确认 | 保留可靠聚合标识，不凭 Key 前缀或用户名猜测 | 脱敏标识，来源／归属显示“信息暂不可用” |

身份校验与必要的 ID／Hash 别名归并是聚合前置步骤，只处理日志中出现的标识，使用缓存和有界批量查找；不可等取出 Top N 后再合并或改变排名。没有可靠映射的无 Hash 记录按未归属处理。

名称、归属名称和状态的展示补充在 Top N 聚合结果产生后执行，避免每次刷新遍历全部 Portal 工作空间。Admin Hash 映射允许缓存，必须兼容未启用 Portal 的部署。

不把“属于哪个应用”实现为自动识别应用。首版以现有 Key 友好名称表达应用用途，不新增应用实体或强制命名规则。

### 6.3 历史状态

- 当前可确认的启用、禁用、撤销、过期或删除状态按来源映射展示；这是**当前状态**，不是请求发生时的状态快照。
- 不能仅因元数据查询为空或失败就标记“已删除”。
- Key 被删除、租户更换密钥、Portal 不可达或当前 Hash 配置无法匹配旧记录时，仍保留日志用量。
- 对不能恢复的历史名称、状态或归属不做补造；前端明确提示信息不完整。
- 不修改或回填历史日志，不保证未曾记录的 Key 身份能够事后恢复。

### 6.4 脱敏

前端只接收名称、脱敏片段及展示用的不透明稳定行标识，不接收完整密钥或 `api_key_hash`。同名、相同脱敏片段的不同 Key 可以用短展示标识辅助区分。

接口、日志、错误信息均不得输出数据库密码、Portal 内部令牌、完整 Key 或完整 Hash。

## 7. 统计口径

### 7.1 请求、成功率与去重

- 统计对象是 ClickHouse 已记录的客户端请求，不是上游尝试次数。重试、故障转移的 `attempts` 不作为额外请求累计。
- `request_count` 为去重后的日志条数；`success_count` 使用日志 `status_code` 的 `[200, 400)` 区间。
- `success_rate = success_count / request_count × 100`。499 等已记录的取消／失败请求参与分母，不计成功。
- 这一口径描述日志中的最终请求结果，不声称恢复未落库的鉴权拒绝或未采集请求，也不改写现有 Gateway 状态码记录逻辑。
- 必须处理批量写入补偿产生的重复日志。首版查询使用与现有 `ReplacingMergeTree` 排序键一致的去重语义，例如 `FINAL`；不能单纯依赖后台合并已完成。
- 相同 `request_id` 但不同请求时间的真实调用，不因客户端复用请求 ID 而被误合并。去重语义按现有日志排序键验证。

### 7.2 Token、费用与占比

- `total_tokens = sum(input_tokens) + sum(output_tokens)`。
- `cached_tokens` 和 `cache_creation_tokens` 单独汇总展示，不再次叠加至总量。
- `total_cost` 汇总日志 `cost`，保留十进制精度，接口使用十进制字符串；展示单位沿用现有网关／首页费用配置，不在浏览器换算币种或重新计价。
- 费用为网关记录的费用，不承诺是上游账单或财务结算结果。没有记录费用的请求沿用原值，不反向估算。
- `token_share = key_total_tokens / all_total_tokens × 100`，与当前选择 Token、请求数或费用排序无关。
- 分母为相同数据源、相同窗口、相同去重口径下的所有日志用量，包含未入榜、已停用／删除及无法归属的历史用量。
- 分母为零时，Token 占比显示 `—`，占比条为空，不产生无穷大或无效数值；有请求但无 Token 的 Key 仍可入榜。

### 7.3 排序与未知用量

- 所选指标降序排列；并列时使用服务端稳定 Key 标识做确定性次序，再截取 10／20／50 条。
- 前端不得只对已经返回的 Top 10 做本地排序来代替更换榜单口径。
- “无法归属的历史用量”单独作为卡片底部的汇总行／提示，显示请求数、Token、费用和占比，不占用 Top N 名额，不冒充一个真实 Key。
- 有无法归属记录时给出明确提示；若全部记录都无法归属，则展示该汇总，而非“该时段暂无调用”。
- 全量统计、未知用量与榜单应基于同一查询窗口及一致读取结果，避免先截取榜单再计算分母。

### 7.4 时间窗口

- 查询窗口采用 `[start, end)`；相对时间从统一的 `end` 回溯，最大 7 天。
- “今日”使用 Admin 现有首页日界线所在的服务端时区，从本地零点到 `end`；不根据浏览器时区重新划分。
- 服务端返回明确的起止时间（含 UTC 偏移）和时区，前端沿用该结果。
- 查询不依赖启用模型列表，因此停用模型的历史调用仍计入所属 Key。
- ClickHouse 明细与现有 Prometheus 今日卡片的采样、落库延迟和覆盖范围不同，不承诺两者数值逐秒完全相等；占比分母使用本榜单自身全量统计。

## 8. API 契约

新增只读接口：

```text
GET /api/v1/dashboard/api-key-ranking
```

| 参数 | 允许值 | 默认 |
| --- | --- | --- |
| `time_range` | `today`, `1h`, `6h`, `24h`, `7d` | `today` |
| `sort_by` | `tokens`, `request_count`, `cost` | `tokens` |
| `limit` | `10`, `20`, `50` | `10` |

缺省值使用默认值，显式非法值返回 400；排序字段只能经白名单映射为 SQL 表达式，不拼接任意用户输入。本接口不支持任意 Key 明文查询、任意时间范围、分页或详情模式。

沿用 Admin 的统一响应外壳。成功响应中的数据包含：

| 字段 | 含义 |
| --- | --- |
| `state` | `ready` 或 `disabled` |
| `data_source` | 固定为 `clickhouse` |
| `window` | `start`、`end`、`timezone` |
| `generated_at` | 该成功结果生成时间；缓存命中不伪造为当前时间 |
| `summary` | 全量请求数、可识别 Key 数、Token 总量和费用 |
| `items` | Top N 榜单数据 |
| `unattributed` | 无法可靠区分 Key 的历史请求数、Token、费用、占比 |
| `warnings` | 元数据部分不可用、存在未归属历史等安全的结构化提示 |

每行包含展示标识、Key 名称、脱敏标识、来源、归属类型／标识／名称、当前状态、元数据可用状态，以及请求数、成功数、成功率、四类 Token、Token 总量、费用和 Token 占比。

权限及错误规则：

- 未登录沿用 401；已登录但非 Root 返回 403，且不得先触发 ClickHouse 或 Portal 查询。
- 未启用 ClickHouse 返回 200、`state=disabled`；没有查询结果，统计字段不伪装为零。
- 查询成功返回 200、`state=ready`；全量请求数为零才显示“该时段暂无调用”。
- ClickHouse 连接、表结构、权限或查询失败返回 503 和可识别的用量数据不可用错误；详细故障仅写脱敏服务端日志。
- 元数据部分失败仍返回 200，保留准确用量，通过行状态与 `warnings` 表示信息不完整。

## 9. 前端刷新与异常状态

- Root 身份解析完成后才挂载组件和发起查询；普通用户不显示卡片，不启动定时器。
- 初次进入或重新激活首页时立即加载；可见且激活时每 30 秒刷新。
- 切换时间、排序、条数立即加载新条件；使用请求取消或序列号，防止慢响应覆盖新筛选结果。
- 使用 Vue 路由缓存生命周期与 `visibilitychange` 配合管理刷新。离开首页、失活、卸载、退出登录或文档不可见时暂停；恢复可见且处于首页时立即刷新。
- 防止重复定时器和重叠请求，不修改其他首页模块原有刷新周期。
- 后台刷新失败时，只能保留**同一筛选条件**的上次成功结果，提示“更新失败”及原数据时间。
- 401／403 或已知 Root 权限失效不适用保留旧结果的规则，必须清空榜单与展示缓存并停止请求；会话恢复沿用现有统一认证流程，不因普通数据源错误触发登出。
- 切换到新的条件后失败，不允许把旧条件的数据放在新标题下；没有匹配条件的成功结果时显示“数据暂不可用”。
- 未配置显示“尚未启用 API Key 用量统计”；后端成功且无调用显示“该时段暂无调用”。
- 不因本卡片失败触发整个首页错误、登出或反复弹出全局提示。
- 默认保持表格可读，不使用点击行样式；窄屏允许表格横向滚动，悬停明细同时支持键盘聚焦。
- 来源、归属、状态、错误和空态文本补齐中文及英文翻译。

## 10. 配置、性能与隔离

- 在 Admin 新增可选的 `[Storage.ClickHouse]` 配置，默认关闭，与管理数据库配置分离。
- 配置覆盖启用开关、连接地址、数据库、只读用户名／密码、TLS、连接与查询超时。示例配置使用环境变量占位，不提交真实凭据。
- 只授予目标 `access_logs` 的查询权限。Admin 不自动建库、建表、迁移、写入或删除 ClickHouse 数据。
- 不因 ClickHouse 未配置或暂不可达阻止 Admin 启动；故障隔离到本榜单。
- ClickHouse 查询超时默认 5 秒；元数据补充共享最多 2 秒预算，并发上限 4，失败以元数据降级处理。
- 用量结果服务端缓存最多 30 秒，相同查询合并并发加载；缓存键包含全部查询条件及部署数据源，返回缓存原有窗口和生成时间。
- 元数据缓存最多 60 秒，因此状态不是即时变更通知；不设置永久的“查不到”缓存。
- 客户端请求取消、超时或失去 Root 权限时及时释放相关资源；任何缓存返回之前都必须完成权限校验。
- 元数据不可用与统计不可用分别记录，不将 Portal 故障扩散为所有 Key 用量不可用。
- 先验证 7 天、Top 50、多个客户端同时刷新时的实际耗时与查询负载；不预先承诺未测量的容量或新增汇总设施。

## 11. 验收与验证

实施阶段至少覆盖：

1. 三类客户端 Key 在一个榜单中正确区分；同名、相同脱敏片段、同用户多 Key 不串账。
2. Admin 缺少 `key_id` 时能按 Hash 区分；可靠 ID 与 Hash 映射不重复计算，冲突不猜测。
3. 租户密钥替换前后用量保持分开，历史元数据查不到不丢用量。
4. 已禁用、撤销、过期、逻辑删除记录仍参与历史统计；查询失败不误标删除。
5. Token 与缓存口径、十进制费用、请求成功率和零 Token 分母正确。
6. 超过 50 个 Key 时，全量排序和分母仍正确；未知历史单列且包含在分母。
7. 补偿重复日志只计一次；请求 ID 相同但时间不同的真实请求不误去重。
8. 今日午夜边界、相对窗口和时区一致；榜单不受当前模型启用状态过滤。
9. 非 Root 直接请求 API 返回 403，且不执行任何数据源查询；普通用户没有组件和轮询。
10. 接口响应、日志、缓存展示对象不包含完整 Key、完整 Hash 或连接凭据。
11. 未配置、空结果、查询失败、元数据部分失败有不同表现；旧请求不覆盖新筛选。
12. 30 秒刷新、筛选立即刷新、隐藏／失活暂停、恢复刷新与退出清理均通过前端测试。
13. 首页其他模块、现有 WebSocket 行为和只读数据库隔离不回归。

自动化测试优先使用模拟数据源与独立测试表。若需要真实 ClickHouse 集成验证，使用隔离数据库／表并提供配对清理步骤，不向生产日志写测试记录。真实数据检查仅执行只读查询。

修改 `.vue`、`.js` 等前端文件后，必须按项目规定运行 Prettier，并执行相关前端测试与构建。后端执行新增单元测试和 Dashboard 相关回归测试；具体命令随实施计划确定。
