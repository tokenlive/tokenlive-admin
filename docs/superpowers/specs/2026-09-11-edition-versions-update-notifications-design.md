# 单机版与专业版版本展示及升级提醒

状态：2026-09-12 已完成 13 项实现任务、逐项审查、整体审查修复及独立复审；隔离环境验证通过。尚未合入原项目、发布或部署；发布依赖和真实 Docker 环境验证仍是独立门槛。详见[交付记录](../plans/2026-09-12-edition-versions-update-notifications-handoff.md)。

本文定义运行中的版本身份、更新判断、权限和网关版本上报，不提供自动安装或升级编排。领域术语见 [CONTEXT.md](../../../CONTEXT.md)，决策理由见 [ADR-0005](../../adr/0005-edition-version-boundaries.md) 和 [ADR-0006](../../adr/0006-server-side-update-check-isolation.md)。

## 1. 范围与目标

- 单机版展示 standalone 整包发行版本；本期升级场景为 Homebrew 安装。
- 专业版展示 Admin 组件版本及 Gateway 版本分布，不引入整套产品总版本号。
- 后端自动发现同一发行渠道的稳定版更新，更新管理员可查看提醒、手动检查及升级指引。
- Gateway 支持轻量版本上报，覆盖现有 Redis 和 HTTP 两种部署通道。
- 保持业务运行独立于更新源、版本查询和版本上报的可用性。

本期不做自动下载、安装、服务重启、数据库升级、组件兼容性求解、完整节点管理、历史节点档案或统一的公开 JSON 发布清单。非 Homebrew 的 standalone 安装不新增专属升级器，也不能被误标为专业版或自动套用 Homebrew 指令。

## 2. 发行身份和展示

| 场景 | 主版本展示 | 更新比较单元 | 更新信息来源 |
|---|---|---|---|
| Homebrew 单机版 | 单机版 `vX` | standalone 整包 | Homebrew 安装源已发布版本 |
| 专业版 Admin | 专业版 · Admin `vA` | 当前 Admin 实例 | Admin 正式 Release |
| 专业版 Gateway | Gateway 版本与节点数量分组 | 每个有效上报的版本组 | Gateway 正式 Release |

### 2.1 运行时身份

运行时显式携带发行形态、当前版本和发行渠道，不能仅凭操作系统、版本字符串、是否启用 Redis 或是否处于合装进程来推断。

- 独立 Admin 启动时明确为专业版，当前版本来自自身构建信息。
- standalone 宿主通过 `adminapp.Options` 向内嵌 Admin 传入单机版身份和 standalone 整包版本。
- Homebrew 包装或启动入口须显式传递 Homebrew 渠道标识；无法确认安装渠道时使用未知渠道，不自动展示 Homebrew 专用升级指令或宣称可以通过 Homebrew 升级。
- 版本缺失、开发构建或无法解析时保留原始显示值，并标记“当前版本无法比较”；不能使用硬编码正式版本填补。
- 后端运行时身份是升级判断依据。前端构建信息仅在后端不可用时作为带有“构建信息”标签的显示回退，不能用于认定运行版本或触发升级提醒。

现有 `/api/v1/pub/version` 的 `version`、`app_name` 保留兼容；新增能力通过结构化字段及鉴权接口提供，不把更新详情或节点身份加入公开接口。

### 2.2 前端呈现

- 普通登录用户可以查看当前发行形态、版本以及 Gateway 的聚合版本信息，不显示更新目标、升级指引或手动检查入口。
- 更新管理员在侧栏版本旁看到“有更新”；“关于”中展示各比较单元的当前版本、目标版本、检查时间和状态。
- 多 Gateway 版本较长时，侧栏显示混合版本摘要，在“关于”展开版本及节点数量，不挤压侧栏布局。
- 至少一个比较单元有有效的“可升级”结果时展示“有更新”。其他单元的未知或失败状态独立保留，不能被合并为“全部已是最新版”。
- 不主动弹窗，不自动打开发布页面；保留现有版本复制功能并使复制内容包含发行形态。
- 版本、时间、发布说明标题等外部数据按文本渲染，不作为 HTML 或脚本执行。

## 3. 更新来源和比较规则

### 3.1 既有发布渠道

单机版读取受控 Homebrew 安装源中 `tokenlive` Formula 的版本声明。只有该安装源已经发布目标版本，才具备 Homebrew 就绪条件；standalone Release 已创建但安装源尚未更新时，不提前提示。

仅解析预期的 Formula 版本数据，不执行下载的 Ruby 或其他代码。解析失败、目标不可访问、响应格式异常或安装渠道未知时返回不可判断状态，不能用 standalone Release 作为替代信号绕过就绪条件。

专业版分别读取 Admin 和 Gateway 仓库的正式 Release 信息，独立更新、独立缓存。仓库定位复用各项目已有发布配置，使用固定的受控来源，不接受浏览器请求临时指定任意更新 URL。

默认仅访问公开发布信息，不要求终端用户配置发布凭据，也不携带用户、租户、模型配置、业务日志或密钥。公开源访问失败或被限流属于“暂时无法检查”，不扩大为新的发布镜像服务。

### 3.2 版本比较

已确认的候选选择规则：Homebrew 以安装源当前 Formula 版本为唯一候选；专业版以对应发布源给出的最新正式 Release（latest）为候选，不遍历历史自行选取语义版本最大值，也不自行按日期排序替换发布源的推荐。候选不满足下面的稳定版条件时，本次没有合法候选，不回退到历史发行来宣称可以升级。

- 仅正式稳定版可作为目标；同时过滤发布元数据中的草稿、预发布标记和版本号中的 alpha、beta、rc 等预发布信息。
- 采用语义版本比较，允许常见的前导 `v`；不得进行字符串排序或仅按发布日期判断升级关系。
- 构建流程明确标识正式构建与开发构建。不能只因某个字符串可解析，就把开发构建当作正式发行。
- 目标高于当前版本：可升级；相同：已是最新版；当前版本高于来源版本：显示“当前版本高于已发布版本”，不建议降级。
- 当前版本未知或不可比较：显示“当前版本无法比较”。即使已获取目标版本，也不宣称该安装可升级或已是最新版。
- 没有取得合法稳定版候选时，显示“暂无可用的稳定版信息”，不等同于“已是最新版”。
- Gateway 各有效版本组分别比较。含未知版本的节点组单独标记，不能掩盖已知组的更新，也不能证明整个部署均已更新。

发现新版仅表示同组件、同渠道存在更高的稳定发行，不承诺该组件能与任意其他组件版本兼容。专业版升级指引应提示先阅读发行说明及部署要求。

## 4. 检查生命周期与状态

### 4.1 已确认的运行默认值

| 配置/行为 | 默认值 |
|---|---|
| 联网更新检查 | 默认开启；通过服务端配置关闭 |
| 自动检查 | 启动后异步检查一次，此后每 6 小时检查，周期可配置 |
| 一轮外部检查超时 | 5 秒，各来源并行检查并共享该截止时间 |
| 手动检查冷却 | 60 秒 |
| Gateway 版本上报间隔 | 30 秒 |
| Gateway 有效上报窗口 | 3 分钟 |

配置在启动时读取；本期不新增在线修改配置的管理页面。关闭联网更新检查时，跳过启动及定时外部请求，手动入口显示已关闭，后端也拒绝触发外部查询。本地版本展示和部署内部的 Gateway 版本上报继续运行。

后台任务由应用生命周期管理，不能阻塞启动、退出或业务请求。定时与手动检查共用检查器；同一 Admin 实例内的并发请求合并，正在检查时返回已有任务状态，不重复联网。

手动冷却以同一 Admin 实例最近一次外部检查的启动时间为基准，所有用户共享该实例的冷却状态。冷却期返回剩余等待时间，不重新请求更新源。多 Admin 实例各自检查，本期不引入全局选主或跨实例检查锁。

读取版本或更新状态的 GET 请求只读本地身份、节点记录和检查缓存，不直接发起外部请求。没有更新查看权限的用户读取当前版本，不会触发更新检查。

### 4.2 状态和历史结果

| 情况 | 展示与行为 |
|---|---|
| 联网检查已关闭 | 已关闭；不允许手动外部检查 |
| 尚未检查 | 尚未检查，不预先宣称已是最新版 |
| 检查进行中 | 检查中；并发入口复用同一任务 |
| 成功取得候选并完成比较 | 按单元显示可升级、相同或当前版本更高 |
| 当前版本不可比较 | 当前版本无法比较，保留原始版本信息 |
| 来源没有合法稳定版信息 | 暂无可用的稳定版信息 |
| 请求、解析或限流失败 | 暂时无法检查；上次成功结果只作为已过期历史信息 |

每个检查单元分别保存最近尝试时间、最近成功时间、错误类别和上次成功结果。失败不能清空其他单元的成功结果，也不能把旧结果包装成本次成功。

读取成功但没有合法稳定候选时，当前状态也必须替换为“暂无可用的稳定版信息”，立即撤销该单元此前的更新提醒；旧候选只能作为过期历史保留，不刷新其最近成功时间。不能同时展示“暂无可用的稳定版信息”和基于同一旧候选的“有更新”。

发布候选与查询新鲜度可缓存，Gateway 的比较结果必须结合当前有效节点分布重新计算；节点新增、版本变化或过期时，复用未过期的发布候选更新展示，不因此额外请求公网，也不保留已经离开统计窗口的旧版本提醒。

超过检查周期而未成功刷新，或本次检查失败后，上次成功结果标记为过期。过期结果可供查看，但不单独驱动“有更新”标记或确定性的“已是最新版”文案。未知、关闭和过期状态不得启用确定性升级操作提示。

## 5. Gateway 轻量版本上报

### 5.1 记录和时效

新增独立的节点版本记录，不把现有请求指标或熔断状态当成节点注册表。

记录只包含部署内的进程实例标识、Gateway 原始版本及正式/开发构建标记等必要元数据。进程实例标识在同一进程生命周期内保持稳定，不使用用户名、租户信息或密钥作为标识；重启后可以生成新标识。

接收端以自身时间或 Redis 过期机制判断记录时效，不依赖上报方自报时间保持记录有效。相同实例的重复上报更新记录，不累加节点数量。

- 启动后异步上报一次，此后每 30 秒上报。
- 3 分钟内有效的上报计入版本分布；到期后从当前分布中剔除，不保留历史节点档案。
- 未收到有效记录时显示“Gateway 版本未知”。
- 新协议收到版本缺失或不可比较的记录时，以“未知/无法比较”分组显示，不使用 Admin 版本填补。
- 老 Gateway 不会上报，无法从缺席上报推断这些节点的数量。界面必须说明统计范围是“最近 3 分钟内有效上报的节点”，而不是完整节点清单或实时健康状态。
- 进程重启后旧标识可能在窗口内短暂保留；窗口到期后剔除。因此数量表示有效上报窗口内的实例，不承诺瞬时存活数。

standalone 不参与专业版节点分布，也不单独触发内含 Gateway 的升级提醒。

### 5.2 Redis 通道

有既有 Redis 通道的 Gateway 通过该通道写入带 TTL 的节点版本记录，不要求再配置 Gateway 到 Admin 的 HTTP 连通性。

记录使用当前部署的缓存命名空间及独立键前缀，隔离不同部署和业务缓存；每个实例一个记录，TTL 与有效上报窗口一致。Admin 从同一命名空间读取有效记录。读取失败必须显示节点信息暂时不可用，不能当成“没有节点”。

节点记录自动过期；测试及清理仅操作本次创建的精确键或专用测试命名空间，不能清空业务 Redis。

### 5.3 HTTP 通道

无 Redis、已有 HTTP 同步配置的 Gateway 使用现有 Admin 地址和同步认证方式发送独立的轻量版本上报，不改变请求指标和熔断状态载荷的语义。

Admin 接收端校验现有同步令牌，并与终端用户的“版本更新管理”权限分开处理。上报失败、超时或旧 Admin 返回不支持，不影响 Gateway 转发业务，也不改为强制启用另一条传输通道。

Admin 有共享缓存时存入共享的时效记录；无共享缓存时使用带时效清理的进程内存储。纯内存模式的统计范围是当前 Admin 已收到的上报，多个 Admin 的内存记录不会自动汇总为全局清单；本期不为此新增注册中心或持久数据库表。

没有可用上报通道时保持 Gateway 版本未知，给出部署内的检查说明，不阻断应用启动。

## 6. 权限和接口边界

统一使用领域术语“更新管理员”：Root 默认具有“版本更新管理”权限，其他用户通过已有角色与 API 资源授权机制获得同等的更新查看、提醒、指引和手动检查能力。

后端必须校验权限并向全局“关于”界面返回能力信息。不能使用用户名判断身份，也不能把当前路由的按钮权限缺省值当成全局更新权限。

接口职责分为四类，具体路由命名在实施计划中与项目现有约定对齐：

| 接口职责 | 授权 | 返回/行为 |
|---|---|---|
| 公开基础版本 | 保持既有兼容范围 | 基础版本与应用名；不返回更新详情、节点身份 |
| 登录后的当前版本汇总 | 普通登录用户 | 发行身份、当前版本、聚合 Gateway 分布及自身更新管理能力 |
| 更新结果读取、手动检查 | 更新管理员 | 结果缓存；或受关闭开关、冷却及并发合并控制的外部检查 |
| Gateway 版本上报 | 既有部署同步认证 | 接收当前部署节点记录，不依赖浏览器登录角色 |

权限不足时后端拒绝访问更新专属内容或触发检查，不能只隐藏前端按钮。向普通用户返回聚合版本信息时不泄露原始节点标识、地址或同步令牌。

## 7. 升级指引

Homebrew 渠道在可升级时提供可复制命令，命令由客户端自身的受控模板生成，不执行远端返回的任意命令：

```sh
brew update
brew upgrade tokenlive
```

对于使用 Homebrew services 托管的安装，另提供以下手动步骤，并提醒重启会影响正在处理的请求：

```sh
brew services restart tokenlive
```

程序只展示和复制命令，不调用 shell、执行升级或重启。安装渠道未知时不直接展示上述专属操作。

专业版分别展示对应组件的发行说明和部署升级指引，不将某个组件更新解释为另一个组件必须同步升级，也不提供未经当前部署方式确认的通用一键升级命令。外部链接限制为预期官方发布/文档来源并使用安全协议。

## 8. 实施涉及的边界

| 仓库 | 必需的改动方向 |
|---|---|
| tokenlive-admin | 运行时发行身份、更新检查器、版本汇总、节点记录读取/接收、权限资源、侧栏及“关于”展示 |
| tokenlive-gateway | 有效的构建版本注入、轻量节点记录及 Redis/HTTP 上报 |
| tokenlive-standalone | 将整包身份和版本传给内嵌 Admin，明确 Homebrew 渠道传递，保持发布源就绪规则 |
| tokenlive-deploy | 对齐 Admin/Gateway 可分别选择版本的配置和升级说明，并兼容原有统一版本配置 |

本期不修改文档站以建立统一发布清单。现有版本注入链中的已知缺口必须随相关实现修正，否则 UI 无法可靠比较版本：

- Admin 发布前端与后端应使用同一正式版本，修正 Makefile 覆盖外部 Release 版本的问题。
- Gateway 入口应实际声明并使用被构建流程注入的版本；二进制和镜像均须携带版本信息。
- standalone 不能只设置前端构建版本或 CLI 版本，必须把整包身份传至提供版本 API 的内嵌 Admin。

不重构与版本功能无关的指标聚合、熔断逻辑、用户体系或部署流程。保留已有工作区与暂存区中的无关改动。

## 9. 上线与兼容

新增接口和字段保持向后兼容，旧的公开版本消费者仍可读取基础字段。建议先发布具备兼容接收与展示能力的 Admin，再发布能够上报版本的 Gateway，最后发布引用这些能力的 standalone。

顺序不同或部分升级时，版本信息可以是未知，业务必须正常运行。旧 Gateway 不上报时不猜测其版本；旧 Admin 不支持新上报时，Gateway 仅记录受控诊断信息，不阻断请求。

已部署且尚未包含本功能的软件，需要先人工升级一次，之后才能自动发现后续发行；本设计不能为未更新的旧程序远程补上检查能力。

专业版内存模式、共享缓存模式的统计范围按第 5 节说明。离线部署通过服务端关闭联网更新检查，仍可查看当前版本及已有内部上报结果。

## 10. 验收标准

### 版本身份与比较

1. 同一 UI 能明确区分单机版整包与专业版组件，专业版没有虚构的总版本号。
2. Homebrew 单机版以整包版本比较，不出现内含 Admin/Gateway 的独立升级提示。
3. 后端不可用时的前端构建回退、缺失版本、开发构建和非语义版本均不触发确定性的升级判断。
4. 稳定版高低、相同、前导 `v`、当前高于源版本、预发布标记与版本字符串不一致均有确定行为；多个历史稳定发行并存时仍遵循发布源的候选选择，不自行改选最高历史版本。
5. Release 已创建但 Homebrew 安装源未更新时无提前提醒；安装渠道未知时不展示 Homebrew 专用升级指令。

### 检查和权限

6. 启动不等待外部网络；关闭开关后，自动和手动路径均无外部更新请求。
7. 自动周期、5 秒超时、60 秒冷却和并发合并用可控时钟与模拟源验证，不依赖真实公网或长时间等待。
8. 请求失败、限流、格式错误、无稳定候选、缓存过期分别显示正确状态；不会误报“已是最新版”。成功读取但无稳定候选时，旧的可升级结果也立即失效。
9. 一个组件检查失败不覆盖另一组件的有效结果；仅有效的可升级结果驱动更新标记。
10. 普通用户、Root、有授权的非 Root、无授权的非 Root 都有前后端权限测试；更改用户名不能绕过权限。
11. 非当前路由的全局“关于”界面仍使用正确权限，不主动弹窗。

### Gateway 与发布

12. Redis-only、HTTP-only 两种通道均可上报；不为 Redis-only 部署强制增加到 Admin 的 HTTP 依赖。
13. 多节点同版本正确计数，混合版本分别显示，重复上报不重复计数；过期、无法比较和完全无上报均正确处理。
14. 接收时间、TTL、缓存不可用、错误同步令牌、重启后旧记录窗口及纯内存统计范围有覆盖。
15. Redis 测试记录有 TTL 和精确清理，HTTP 内存记录到期剔除，不产生持久业务脏数据。
16. 正式二进制、镜像、standalone 内嵌 API 与相应前端构建能对应正确的发行版本和渠道。
17. 只复制指令或打开受控链接，任何检查、提醒和上报路径均不执行安装命令或重启服务。
18. 修改前端文件后按项目要求执行 Prettier；相关 Go 与前端测试在实施阶段实际运行，不能以本文的验收清单代替测试结果。
