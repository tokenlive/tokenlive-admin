# 供应商监控采用上游健康视角而非业务量视角

Status: accepted

供应商详情页的监控只回答"这家上游依赖现在可靠吗"（端点可用性、熔断状态、上游调用成功率、配额余量），不重复 Dashboard 与模型详情页已有的业务量分析。故障转移场景下，一次用户请求产生的多次上游调用各自归属于被调用端点所属的供应商：从供应商 A 转移到 B 的请求，A 记失败、B 记成功。

这使系统中存在两个分母不同的成功率，我们为其确立不同名称以防跨页面误读：**Upstream Call Success Rate**（上游调用成功率，供应商侧，故障转移走掉的计为失败）与 **Request Success Rate**（请求成功率，业务侧，转移后成功即计成功）。供应商页的价值恰恰在于暴露"A 挂了多少次"这一信号，若沿用业务口径，A 的失败会被故障转移完全掩盖，页面即丧失预警能力。

选择该定位的决定性理由是数据可得性，而非单纯的价值判断：现有后端中 `trends` 支持 `group_by=provider`、熔断接口返回 `provider_id`、事件支持按供应商过滤，而 `model-ranking` 的 Prometheus 分支硬编码 `by (model)`、`model-performance-trends` 强制要求 `model=` 匹配器。照搬模型页的 8 个 KPI 与 4 张图反而是成本最高的路径——其中 7 个 KPI 与 2 张图在后端均无 provider 维度实现。

Consequences:

- P50/P95/P99 分位数不在供应商页提供。内存 store 仅累积 sum/count 而无直方图桶，分位数只能由 Prometheus 的 `histogram_quantile` 计算，而 `gateway_*_bucket` 是否带 `provider` label 无法从 Admin 仓库验证。一个在部分部署下静默消失的指标不如不提供。
- 上游 429/401 专项计数不在范围内。`event_log` 无 HTTP 状态码字段，且其 `rate_limit` 事件指本平台限流策略命中，并非上游返回的 429。从 `message` 文本解析状态码会因一次文案调整而静默失真，这类"看起来可用"的指标比缺失更危险。该能力的真实依赖是 Gateway 埋点补充，作为独立议题推进。
- 时间范围限制在 7 天以内。Prometheus 保留期通常数月，内存 store 硬上限 7 天；限制范围使三条数据源路径行为一致，而不是暴露不一致再要求前端向用户解释部署细节。
