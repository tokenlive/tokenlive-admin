# 供应商密钥稳定标识与端点级联同步机制

Status: accepted

## Context

`Endpoint.api_key` 原先同时承担了“多 Key 导入端点拷贝保存的供应商密钥”和“端点手动覆盖的独立密钥”两种职责，且供应商 `api_keys` JSON 数组条目仅包含 `{value, description}`、没有稳定身份标识。`Provider.Update` 依赖数组下标对齐计算密钥变更并按旧明文批量更新端点，导致用户执行先删后增、调整顺序或删除中间某条密钥时出现漏更新甚至跨密钥错改；同时缺少删除密钥时对关联端点的保护语义。

## Decision

- **引入稳定密钥身份**：为供应商每条 `ApiKeyItem` 分配不可变 `id`（XID），在 `Endpoint` 增加可空 `provider_key_id` 字段，显式区分 **密钥绑定**（`provider_key_id != ""`）、**密钥继承**（`provider_key_id == "" && api_key == ""`）与 **密钥覆盖**（`provider_key_id == "" && api_key != ""`）三种模式。
- **双写镜像 `endpoint.api_key`**：在 **密钥绑定** 模式下，创建或级联更新端点时同步将供应商密钥明文镜像写入 `endpoint.api_key`，保证网关同步、`ResolveCall` 及现有连通性探测继续读取 `endpoint.api_key`，无需全面重写下游读取链路。
- **删除密钥或切换为 OAuth 时自动禁用关联端点**：当供应商删除某把已被绑定的密钥（或从 `api_key` 切换为 `oauth_token`）时，保存前预检受影响端点数并经前端二次确认，确认后将关联端点自动设为禁用（`enabled = 0`）并清空 `provider_key_id`，但保留原 `api_key` 值以防误重新启用时意外滑入 **密钥继承**。
- **冲突拦截与存量兼容**：禁止同一供应商保存重复值密钥，且级联更新前检测是否会与同模型现有端点触发路由身份冲突，冲突则事务回滚报错；服务启动幂等回填结合更新兜底，按同供应商同明文自动认领历史存量端点的 `provider_key_id`。

## Consequences

- 供应商调整密钥顺序、原地改值或增删部分密钥时，已导入端点的级联同步不再受数组下标影响；手工覆盖密钥的端点严格隔离不被误改。
- 单 Key 导入继续保持 **密钥继承**（留空），仅多 Key 导入及显式绑定场景使用 `provider_key_id`。
- 端点的创建、更新与供应商级联同步需维护 `provider_key_id` 与 `api_key` 的一致性（包括外部无 `id` 调用时的按值兼容匹配），并在审计日志与 Redis 同步中覆盖被级联变更的端点。
