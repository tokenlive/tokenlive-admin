01

配置准备与下发

管理操作触发，不是每次聊天请求都执行。三种配置交付方式互为替代，不是依次经过的三个服务。

DB 保存成功 ≠ Gateway 已同步成功。改名、启停、删除同样走配置维护与缓存撤销；图中省略重试恢复细节。HTTP / 嵌入快照由数据库生成，Redis 路径原子更新运行时文档与刷新版本。

02

单次请求：裁决 → 选模 → 执行 → 返回

POST /v1/chat/completions · model=复合模型编码 · stream=false。列是逻辑职责，不代表新增部署服务。

配置不变量

  • 至少两个不同的普通子模型，不允许复合嵌套。
  • 0–100 全覆盖、无重叠；只有最后一段含上界 100。
  • 区间决定正常命中，不另设“未命中默认模型”。
  • 请求固定配置版本，更新不打断在途请求。

两种异常，不同处理

  • 裁决失败：选择最高档可用候选，评分为空。
  • 目标失败：先端点重试，再尝试更高档。
  • 禁止降档、重复裁决和无限重试。
  • 硬额度、取消、不可重试错误不能被升级绕过。

隔离与验证边界

  • 原请求元数据用于治理匹配，上游传输凭证隔离。
  • 裁决 usage 独立；每笔配额按原桶核销。
  • MVP 仅文本、非流式 Chat Completions。
  • 机制已验证，真实模型裁决效果待实测。
